# ToME 技能查看器：可行性分析与实现方案

> **本文件是项目初期的可行性研究**，数字是当时的。
> 当前总量与测试基线见 [HANDOVER.md](HANDOVER.md) §0。


本文记录新项目 `modern_tome_viewer` 的调研过程、结论与关键设计决策。

## 1. 结论速览

| 问题 | 结论 |
| --- | --- |
| 数据是否够用？ | **够用**。379 个技能大系、1826 个技能，字段覆盖使用模式、冷却、使用速度、射程、资源消耗、升级需求、完整技能文本 |
| 高级搜索是否可行？ | **完全可行**，且无需后端。数据总量 2.6 MB（gzip 后约 600 KB），浏览器内存索引只需 ~80 ms |
| 结构化筛选是否可行？ | **可行**。所需字段都能从原始数据解析或推导，职业适用范围可由现有映射反查 |
| 主要风险？ | 少数数据脏值（已修）、上游缺 65 个图标（已降级处理）、多语言（上游只有中文） |
| 交付形态？ | 纯静态站点，`npm run build` → `dist/`，可托管任意静态服务器 |
| 已交付范围？ | 高级搜索 + 结构化筛选 + 技能详情 + 大系/职业/种族浏览 + 收藏 + 对比 |

## 2. 参考项目现状

### 2.1 `starsapphirex.github.io/tome-viewer`

仓库里**只有 Next.js 的静态构建产物**，没有源码：

```
tome-viewer/
├── index.html, 404.html
└── _next/static/chunks/
    ├── app/viewers/{classes,races,skills}/page-*.js   # 三个页面
    ├── app/layout-*.js                                # DataProvider（数据加载逻辑）
    └── 739-*.js, 456-*.js, ...                        # 主题、MUI、字体
```

反编译 `739-*.js` 里的 `DataProvider` 可以看出它的数据流：

1. 依次 fetch `data/master/{tome,classes,races,search.talents-types}.json`；
2. 遍历 20 个技能分类 × 3 个版本（1 / 1.3 / 1.5），fetch `talents.<分类>-<版本>.json`；
3. 把结果缓存进 `{ "talents/spell/fire|1.5": [...] }` 这样的字典；
4. 页面按「大系」分组展示技能，点击技能弹出详情。

**它的检索能力**：首页 `app/page-*.js` 实际上只是 `router.push('/viewers/classes')`；
技能页只有一个「大系」侧边栏，没有搜索框。真正意义上的搜索只存在于 `tometips` 老站点
（Bloodhound + typeahead，对 `search.talents.json` 的 `name` 字段做 n-gram 匹配）。

**结论：原项目在检索维度几乎是空白，这正是新项目要补的部分。**

## 4. 技术方案与取舍

### 4.1 技术栈

Vite 7 + React 19 + TypeScript + Tailwind CSS 4。理由：

- 纯静态输出，`base: './'` 让产物在 GitHub Pages 子路径、`file://`、任意静态服务器下都能跑；
- 构建体积小（当前 237 KB JS / 75 KB gzip），无 UI 框架负担；
- 类型化数据模型让「字段解析」这类容易出错的地方能在编译期发现。

### 4.2 搜索：为什么不用现成库

先试了 FlexSearch 0.8 的 Document API，实测对中文子串检索失效：

```
query 寒冰      -> []            (文档含「寒冰之矛」)
query 火焰伤害  -> []            (文档含该串)
query 火焰      -> 只命中 tree 字段
```

原因是它的 query 侧 tokenize 与索引侧不一致，且 Document API 难以表达「某词只在某字段匹配」。

改为**自研倒排索引**（`src/lib/search.ts`，约 400 行、零依赖）：

- **分词**：CJK → 单字 + 相邻双字（`火焰冲击` → 火, 火焰, 焰, 焰冲, 冲, 冲击, 击），
  因此 `火焰`、`焰冲` 都能命中；ASCII → 小写词，支持前缀扩展。
- **多词项求交**：一个检索词可以包含多个 token（`tree:spell/fire` → spell + fire，
  中文长词 → 多个单字/双字），要求**同一文档命中全部 token**，
  这样 `tree:spell/fire` 表示「法术系下的火焰大系」，而不是「任意法术或任意火焰」。
- **排序**：`字段权重 × 词项数 × 最大 IDF × (1 + log tf)`，字段权重 name 12 / tree 6 / category 3 / text 1。
  实测「火焰」榜首为「火焰之躯」，名称命中稳定压过正文命中；`火焰`（双字）比单字 `火` 权重更高。
- **语法**：`field:term`、`"短语"`、`-term`，支持斜杠路径（`tree:spell/fire`）；
  未知前缀（如 `cooldown:5`）退化为普通文本。
- **索引内容**：技能名 + 英文 short_name + 内部 id、大系名 + 大系 id、分类名 + 分类 id、技能正文纯文本。
- **性能**：1826 文档、约 3.5 万词条，索引构建 81 ms；
  最坏情况（多词 CJK）单次查询约 0.5 ms，输入即出结果。

### 4.3 筛选：谓词编译 + 分面计数

- `compileFilters()` 把筛选状态编译成闭包，多选值预先转成 `Set`，
  避免每次按键对 1826 条数据做 `Array.includes`；
- `facetCounts()` 计算某个维度各选项的命中数时，会**先剔除该维度自身**的条件，
  这样数字回答的是「勾上这个选项还能剩多少条」，而不是一个恒等于 0 的交叉结果；
- 数值区间采用「区间与阶梯有交集即命中」的语义，与游戏里冷却随等级变化的实际表现一致；
- 全部筛选状态序列化进 URL hash，可直接分享/收藏，也支持 `?talent=T_FIRE_STORM` 深链。

### 4.4 数据体积优化

| 措施 | 效果 |
| --- | --- |
| 只保留 1.5 变体 | 6.5 MB → 2.4 MB（原始输入） |
| 去掉前端可推导字段（`plainName`、`source`、展开后的 `cooldown/range/cost` 对象） | 3.2 MB → 2.6 MB（输出） |
| 图标只复制被引用的 1704 个 | 9.3 MB → 8.7 MB |
| 图标按需 `loading="lazy"` | 首屏不加载全部图标 |

产物 gzip 后：JS 75 KB + CSS 5 KB + 数据约 600 KB。

## 8. 收藏与对比的实现

- 两者共用 `useIdList` 钩子（`src/hooks/useIdList.ts`）：localStorage 存有序 id 列表，
  读取时跳过已不存在的 id，写入失败（隐私模式）静默降级。
- 对比上限 6 个，超出时 `limitReached` 置位并在底部对比栏提示，不会静默丢弃。
- 最优值判定抽到 `src/lib/compare.ts`（无 React 依赖，可直接单测）：
  冷却取等级阶梯最小值、射程取最大值、资源取解析出的数值，方向分别是最低/最高/最低。
- 详情面板、结果行、收藏页都能加入对比，底部固定对比栏实时显示已选技能。

## 9. 技能数值模拟的实现

技能说明里的数字是游戏用公式算出来的。要让它可调，必须先把公式**反过来解**：

1. **解析**：每个 `<acronym>` 的 title 列出输入（技能等级 1-5、技能系数、法术强度…），元素文本是这些输入下的数值阶梯。
2. **公式**：实现 `combatTalentScale` 与 `combatTalent{Spell,Mind,Physical,Steam}Damage`、`combatTalentStatDamage`
   （源自 `tome/mod/class/interface/Combat.lua`，含 `rescaleDamage` 的 1.04 次幂）。
3. **反解**：伤害公式对 `(base, max)` 线性，但只有一个 power 值时两者不可分离，
   因此在 base∈[0,300] × max 的粗网格上搜索，再做逐步收缩的局部精修；
   同时枚举 mastery 候选（1.3 为主），取残差最小者。数据里 88% 的数值可解到残差 <5%。
4. **重算**：`evaluateAcronym` 用解出的 base/max + 用户滑条值代入公式；
   技能系数按 `mastery × coefficient / 1.5` 作用于有效技能等级。
5. **性能**：反解在 `npm run data` 阶段完成（约 80 秒），结果写进 `talents.json`，
   浏览器只做一次线性计算，滑条拖动无延迟。

未能反解的 12%（参数本身是阶梯、或 `角色等级` 这类无固定驱动量的写法）在悬停时只显示数据参考值。

## 10. 数值模拟：优先源码，兜底反解

2026-09-10 已接入 Lua 静态提取。详见 [Lua 源码管线](lua-scaling.md)。

伤害公式在固定强度 P 下只能辨识 `max*(base+P)/(base+100)` 这个幅度。五个技能等级点
不能唯一反解 base/max，尤其 P=100 时 base 完全消去。此前关于「五点两未知数是超定系统」
及「只有 base=95/max=267 能复现火焰冲击」的结论不成立。

火焰冲击源码的实际系数是 10/250，技能系数 1.5 时输出 `181,246,297,340,378`。
现在先沿 info 参数追踪纯 getter 和公式，再校验全部参考点，只有唯一匹配者才能作为源码结果。
完整表达式保留取整、倍率、Limit、raw、log、属性递减等信息，不强行压成两个系数。

当前 3335/3750 个数值可调（88.93%），其中 1225 条有源码公式、2110 条仍为反解估算；
415 条只显示参考值。源码缺失、表达式不受支持、输入维度不支持、曲线冲突或版本差异都会阻止源码匹配。
这不代表拥有源码就能达到 100% 覆盖；还需要解析导出器、说明变换、跨技能状态与 DLC 运行时修改。

日常检查新增 26 项数值测试，包含真实游戏 Lua 执行生成的 1200 组基准及全量参考点检查。
verify 现在明确校验火焰冲击的系数、参考阶梯和强度 300 的结果；浏览器测试验证这些数据实际显示并随滑条准确变化。
